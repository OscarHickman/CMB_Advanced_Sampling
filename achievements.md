# Achievements — DiffCMB

*Condensed record of what's validated and closed out — current state, not a change log. Full debugging history is in git log. Forward plan: `ROADMAP.md`.*

## Validated foundations

- **Phase 0 — unlensed Gibbs baseline on real Planck data (lmax=300, float64): converged and trusted.** Reference everything downstream is checked against.
- **Phase 1 — differentiable lensing operator**: gradients w.r.t. both alm and φ validated against finite differences and an independent gold-standard Jacobian.
- **Phase 1.5 — dense SHT matrix eliminated.** Matrix-free ducc0 SHT behind `tf.custom_gradient` (~500x under the speed gate; the dense path didn't fit in GPU memory). This is what makes lmax=300+ tractable at all.
- **HMC + matrix-free-SHT alm sampler — production path, validated.** ~31x better net ESS/wall-clock throughput than the old dense-SHT reference (which replaced the abandoned messenger-field route, below). Requires MAP initialisation before burn-in — without it, burn-in looks like unresolved drift even though the sampler itself is correct.
- **Phase 2 pre-production gates, both resolved.** (1) Joint (alm, φ) mixing at lmax≤50 is marginal, not pathological — HMC on both blocks needs no reparametrisation. (2) An unlensed-operator exact-Gaussian shortcut for alm|C_ℓ was **rejected** (652% worst fractional bias in C_l^TT — weak lensing isn't norm-preserving enough at this S/N). HMC-on-both-blocks is the production configuration.
- **Matrix-free port of the φ-block (Block 3) lensing operator — done, full-sky and masked-sky validated.** Full-sky matches the dense reference to numerical precision; masked-sky validated by finite differences directly on the matrix-free path (the dense path isn't a valid masked-sky reference at nonzero φ).
- **Beam transfer function + HEALPix pixel window — validated, opt-in** (`beam_fwhm_arcmin=None` on `CosmologyAdvancedSampling`, `None` = old behaviour). Validated against an independent ground truth (`healpy.almxfl`+`alm2map`).
- **Anisotropic per-pixel noise — validated, opt-in** (`noise_map=None`, `None` = old behaviour). Validated against an independent ground truth.
- **Block 4 — C_L^φφ|φ exact inverse-Gamma draw — validated, opt-in (`sample_cl_phiphi=True`).** Same exact-conjugacy argument as Block 1's C_ℓ|alm draw. Validated against a brute-force cross-check and a 3000-realization recovery test. Resamples the φ prior spectrum every sweep and rebuilds the φ mass matrix to match; mutually exclusive with any non-diagonal φ mass matrix (`'fisher'`/`'block'`, below). Full checkpoint save/resume support.
- **φ-block memory leak — root-caused and fixed at lmax=32** (eager `tf.py_function` calls leaking TF's process-global registry; fixed by tracing `bootstrap_results`+`one_step` together in `@tf.function`, ~20,000x RSS reduction). **Caveat: recurred at lmax=128** in a later coverage-pilot run (OOM after ~1200 sweeps) — fix holds at the scale validated, not confirmed to fully close the leak at production scale. Workaround: restart the process periodically.
- **lmax=300 point-validation run at `phi_n_lfs=80`: chain is healthy, φ-amplitude deficit is under-mixing, not sampler geometry.** Recovered φ power under-estimated by roughly half to seven-eighths across l=10-300; deficit decreases smoothly with S/N (Spearman ρ=-0.78) — the signature of an under-mixed start, not HMC correlation-length degradation. Same phenomenon as the lmax=128 stuck-bin finding below, at a different scale. Not being chased with further lmax=300 compute — resolving the φ-equilibration track (below) makes this moot.

## φ-block equilibration: root cause found and fixed (2026-08-17→18)

The central blocker for the whole project since lmax≈128 pilots began: the φ block (Block 3) fails a fixed equilibration gate (worst lag-1 autocorrelation < 0.9, worst drift < a few σ, phi accept ≥ 0.15) needed before the coverage/rank ensemble (the paper's headline exactness evidence) can be trusted. Every attempt below is a real, ruled-out hypothesis — don't retry without new evidence.

**Ruled out, in order tried:**
1. **Tuning axes (resolution, window length, trajectory length, integrator) — all NO-GO, none closes the gate.** phi_n_lfs 80→240→480 is non-monotonic (can regress a previously-passing bin); lengthening the window 3700→7000 sweeps buys marginal not qualitative improvement; dropping lmax 128→64→32 relocates the stuck bin rather than removing it. MCLMC (isokinetic leapfrog, `diffcmb/mclmc.py`) wins ESS/wall-clock-second at every probed bin but fails the actual equilibration gate twice (untuned and step-size-tuned), including one run where careful nside=128 step-size tuning made lag-1 autocorrelation *worse* (≈1.000 vs ≈0.975-0.99 untuned).
2. **Harmonic band-edge hypothesis — tested, falsified.** The stuck bin is not reliably the one nearest the lmax cutoff (a middle bin failed worse than the edge bin in a directly comparable lmax=128 run).
3. **Diagonal Fisher mass matrix (one-shot burn-in estimate) — NO-GO, and worse than no preconditioning** (worst lag-1 0.999, worst drift 7.19σ vs the plain run's numbers). Closed as unfavorable.

**Root cause, confirmed 2026-08-17 (job 11774832):** the φ-block posterior has significant **cross-L Hessian coupling** — perturbing a coordinate in one L-bin measurably changes the gradient in a different L-bin (mean coupling ratio 0.26-0.62 between distant bins, up to 0.97 at individual points). This is *comparable in magnitude* to the within-bin curvature a diagonal mass matrix captures. It explains every failure above: no diagonal-in-L preconditioner (prior-only or Fisher) can represent curvature that lives *between* L-bins.

**Fix implemented and unit-tested 2026-08-18: `phi_mass_matrix='block'`, a per-m-block Nystrom cross-L correction.**
- `lensing.py::estimate_phi_block_hessian` groups φ coordinates by (channel, m) — the same grouping used for the analogous alm Block-2 problem (`messenger.py::build_block_cholesky`, where same-m coupling was found to dominate; carried over as a plausible but not independently re-verified assumption for φ specifically — **if the block pilot below is NO-GO, check this assumption first**, via an m-resolved version of `diagnose_phi_hessian_coupling.py`). For each block, a low-rank Nystrom approximation of the true Hessian is built from a handful of single-coordinate FD gradient probes (the same validated FD method `estimate_phi_diag_fisher` uses).
- `samplers.py::build_phi_block_mass_chol`/`PhiWhitener` fold this into a per-block Cholesky whitening, one-time burn-in estimate (frozen thereafter, like `'fisher'`), mutually exclusive with Block 4.
- Two real bugs caught during testing: (1) a fixed absolute eigenvalue-clipping floor caused ~10^15x blow-up since curvature scale varies hugely across L — fixed with a scale-relative floor; (2) `tf.gather` produced ambiguous `IndexedSlices`/dense gradients inside TFP's traced leapfrog loop — fixed by forcing a dense gradient through `scatter_nd` (`samplers.py::_dense_grad_gather`, a reusable pattern for future preconditioning code). 9 new tests, full suite green (101 passed/1 skipped).
- `pilot_coverage_equilibration.py` gained `--phi_mass_matrix {prior,fisher,block}` (was hardcoded to `'prior'`+Block4-on) and forces Block 4 off automatically for `fisher`/`block`.

**Pilot status:**
- **lmax=64, NUTS comparison track (job 11781382): NO-GO, harvested 2026-08-18.** Worst lag-1 autocorrelation 0.985 — dynamic trajectory length alone doesn't help, as expected (still diagonal mass matrix). Confirms this was never the fix; no further NUTS-alone tuning planned.
- **lmax=64, block mass matrix (job 11781626): GO, harvested 2026-08-18.** Worst lag-1 autocorrelation 0.557 (< 0.9), worst drift 0.20σ (< 2.0σ) — the trace scatters about a stationary level instead of sliding toward truth. **This closes the equilibration blocker at lmax=64**: the cross-L Hessian correction is confirmed as the fix, not just a hypothesis.
- **lmax=128 scale-up: NO-GO, harvested 2026-08-22 (job 11830353, third and final resume of the chain started as job 11795998).** Full 400 burn-in + 3300 samples completed (9h11m for the last 600-sweep resume leg, ~10s/collected-sample). Worst lag-1 autocorrelation **0.996** in the lowest-L bin `[2,10)` (gate is <0.9) — this bin's lag-200 autocorrelation is still 0.559, i.e. essentially unmixed over the whole run. Lag-1 is **monotonic in L** — 0.996, 0.983, 0.813, 0.681, 0.588 from `[2,10)` to `[100,128)` — i.e. mixing degrades smoothly toward low L. The failure is worst at low L but is not confined there: `[60,100)` also carries a long slow component (r_200 still 0.349) and a drift of **-1.80σ**, marginal against the 2.0σ gate. Phi accept rate fell to **0.238** (vs **0.670** at lmax=64) *at a smaller* phi step size (2.418e-2 vs 3.839e-2) — a smaller step buying a much worse accept rate means the integrator is accumulating energy error, i.e. the preconditioner itself degraded, not merely a step-size mistune. Output: `results/analysis/pilot_coverage_lmax128_block_n3300.npz`. lmax=64 passing doesn't guarantee lmax=128 does, confirmed.

- **lmax=64, production configuration — Block 4 (C_L^φφ) ON + `phi_mass_matrix='block'` (job 11836793): NO-GO, harvested 2026-08-24.** First gate of the actual paper configuration (previously only Block 4 OFF had been gated at lmax=64). Worst lag-1 autocorrelation **0.945** (gate <0.9) in bin `[30,60)`; drift stayed within gate (worst -0.50σ). This is markedly worse than the Block-4-off run at the same lmax (job 11781626: worst lag-1 0.557) — turning Block 4 on measurably degrades φ mixing at a scale that otherwise passes. Phi accept rate 0.645 (healthy, well above the 0.15 floor), so this is not a step-size/acceptance problem. Notably the low-L bin `[2,10)` that failed at lmax=128 is *fine* here (r_1=0.761, first lag<0.2 at lag 10) — the newly-worst bin is mid-L, a different failure location than the lmax=128 low-L result, suggesting Block 4's effect is not simply "makes the existing low-L weak spot worse" but introduces its own coupling. Output: `results/analysis/pilot_coverage_lmax64_block_cl4_n3300.npz`. Consequence: the mutual-exclusivity guard relaxed on 2026-08-23 produces a technically-runnable but not-yet-equilibrated configuration — the joint (C_ℓ, C_L^φφ) headline figure is still blocked pending a fix. Reported per the standing no-unilateral-tuning rule; next step needs user sign-off.

**Leading hypothesis (2026-08-23, not yet tested): fixed Nystrom rank vs. growing block size — a rank-deficiency problem, not a grouping problem.** `estimate_phi_block_hessian` uses `n_probes=6` (default, and `run_gibbs_chain`'s `phi_block_n_probes=6`), a *constant*, while blocks are grouped by (channel, m) so block size is `K ≈ lmax − max(2,m) + 1`. The m=0 block therefore has K=63 at lmax=64 but K=127 at lmax=128: the same rank-6 Nystrom approximation covers 9.5% of the block at lmax=64 and only 4.7% at lmax=128. Crucially, a φ coordinate at multipole L exists only for m ≤ L, so **all L<10 coordinates live exclusively in the m=0..9 blocks — the largest, least-well-approximated ones** — while high-L coordinates are spread across all m including the small, near-exactly-captured high-m blocks. This predicts precisely the observed monotonic-in-L degradation, predicts it appearing on the 64→128 scale-up, and is corroborated by the accept-rate/step-size signature above. It also predicts the *inversion* seen across the fix: pre-fix at lmax=64 the stuck bin was the **top** bin `(60,64)` (per `diagnose_phi_hessian_coupling.py`'s hardcoded `stuck_bin`), and post-fix at lmax=128 the worst bin is the **bottom** one — consistent with a correction that works well on small (high-m) blocks and poorly on large (low-m) ones.
- This is a *different* hypothesis from the "check the same-m grouping assumption" note recorded in the block-mass-matrix entry above: that one asks whether grouping by m is the right structure; this one says the grouping may be fine and the *rank within each group* is the deficiency. They imply different fixes (restructure blocks vs. raise/scale `phi_block_n_probes`).
- **Testable offline, without an MCMC pilot**: at a saved chain point, compute the m=0 block's true (K,K) Hessian by taking all K gradient columns (~127 gradient evals, minutes) and measure Nystrom reconstruction error and whitened condition number as a function of rank 6/16/32/64. That is a deterministic diagnostic costing hours, not a multi-day gate run.
- Not yet attempted — reporting per the standing no-unilateral-tuning rule.

## Real bugs found and fixed (dense-reference validation catches, not derivation trust)

- **φ-block HMC gradient**: a finite-difference backward pass could re-query a shifted angle into a different bilinear-interpolation cell, producing wild step-size-dependent gradients — replaced with an analytic gradient.
- **alm precision convention**: uniform 1/C_ℓ used where the real spherical-harmonic convention requires 2/C_ℓ for m>0.
- **Messenger conditional derivation**: the plausible naive `t|s,d` precision was subtly wrong (needs the reduced noise N−T); caught against an exact dense reference before touching production.
- **SHT operator normalisation**: AᵀA is not a scalar multiple of identity — needs per-mode m=0/m>0 weights *and* empirical calibration (HEALPix quadrature is ~1-2% off the analytic constant).
- **HMC + matrix-free SHT JIT-compile incompatibility**: `jit_compile=True` can't compile through `tf.py_function` — silently never ran until a one-line fix disabled JIT for that path.
- **`tf.gather`/`IndexedSlices` on a custom-gradient output**: `tf.gather` on a `tf.custom_gradient` op's output produces `IndexedSlices`, not a dense tensor, as the upstream cotangent — any `.numpy()`/`tf.py_function` call inside that op's backward pass must `tf.convert_to_tensor()` it first. A second, reverse-direction instance of this same class of bug (the gather's own backward pass being ambiguous, not a downstream consumer) hit the φ-block whitener in 2026-08-18 — see the block-mass-matrix entry above.
- **Cosmic variance mistaken for sampler bias**: an early validation script compared posterior C_ℓ^TT draws against the CAMB *ensemble-average* spectrum, producing spurious multi-sigma "bias" at low l from ordinary cosmic variance. Fixed by comparing against the *realized* power in the actual drawn alm_true instead.
- **`integrated_autocorr_time`'s zero-variance short-circuit was a hidden absolute-tolerance bug**: `np.allclose(x, 0.0)` used a hardcoded `atol=1e-8`, but phi-power summary statistics are naturally O(1e-9)-O(1e-17) — real fluctuations were misread as "no variance" and silently reported as fake ESS=100%. Fixed with a scale-relative check.
- **`lensing.py` never converted author↔healpy alm ordering (found 2026-08-24).** `_alm_packed_to_hp`/`_alm_hp_to_packed` indexed with the *author*-ordering formula `L*(L+1)//2 + m` and handed the result straight to healpy/ducc, which are m-major (`hp.Alm.getidx`). `almmotho`/`almhotmo` — which exist for exactly this conversion, and which `samplers.py::_packed_to_alm_ho`/`_alm_ho_to_packed` do call — were never invoked. `hp.Alm.getidx(127,2,2)=255`; the code wrote that coefficient to index 5. Every coefficient therefore sat at the wrong multipole on the sky: the C_ℓ / C_L^φφ prior that Blocks 1 and 4 apply per multipole was applied to modes living at a different multipole in the likelihood's SHT. Measured effect: packing a `synalm` draw gave `S_ℓ/(2ℓ+1)/C_ℓ` = 1.95 at ℓ=30 (≫5σ); after the fix, 0.90 (σ=0.18), mean 0.972 for ℓ≥30. **Why it survived so long: the wrong index map is a bijection, so `packed→hp→packed` round-trips exactly** — `test_alm_format_round_trip` passed throughout — and `test_compute_sl_phi_np_matches_brute_force_healpy_ordering` hardcoded the *same* wrong formula on its "independent" reference side, so it agreed with the code by construction rather than checking it. Lesson: a round-trip test cannot catch a consistent permutation; only a test pinning an *absolute* (L,m) can. Now covered by `test_alm_hp_to_packed_uses_true_healpy_ordering` (single-mode delta → asserted packed slot) and `test_packed_sl_matches_healpy_power_per_multipole` (exact, non-statistical). φ went through this path in production (`lensing.py` deflection field and `psi_lensed`), and every script built its `alm_true_packed`/`phi_true_packed` "truth" through it, so **all pre-2026-08-24 φ-block results are invalid and must be re-run.**
- **`run_gibbs_chain`'s return-tuple arity depends on which blocks are enabled** (4-tuple with no φ block, 5-tuple with φ, 6-tuple with φ+C_L^φφ) — a script hardcoded a 5-tuple unpack for a no-φ-block call, crashing *after* a full 3000-sweep chain completed. SLURM reported `COMPLETED, exit 0:0` since the traceback was inside Python after the job's own work was done — always check `.err` for a traceback, not just SLURM job state, when harvesting completed jobs.

## Closed-out sampler routes (do not revisit without new evidence)

- **Diagonally-preconditioned CG on the masked sky: abandoned.** Jacobi preconditioner degrades ~4 orders of magnitude under a realistic mask; extrapolated cost 10⁴-10⁵ iterations per Gibbs step.
- **Messenger-field sampler: built, validated at small scale, closed as non-viable at production scale.** Conditionals correct against dense references, but the production run showed intrinsic critical slowing down at n_alm≈90k (ESS 0.6%, C_ℓ biased low, monotonic drift). Superseded by the HMC + matrix-free-SHT pivot above.
- **Unlensed-operator exact Block-2 shortcut for alm|C_ℓ: rejected** (Phase 2 pre-production gates above). Not fundamentally dead — a CG solve built from autodiff of the lensed posterior could target the correct conditional exactly — but unexplored and not worth pursuing unless HMC-on-both-blocks becomes a proven throughput bottleneck.

## Engineering gotchas worth remembering

- **Eager-mode `tf.py_function` calls in a hot loop leak memory** — wrap in `@tf.function` instead. A value that must reach a traced function and changes between calls must be a `tf.Variable` read via `tf.convert_to_tensor`, not a plain Python/numpy value closed over — the latter gets silently baked into the trace as a constant.
- **`/cosma/apps/durham/dc-hick2` has its own NFS quota** (100GB / 10M files, `quota -s` not `lfs quota`) shared across all of dc-hick2's project directories, not just diffcmb.
- **`/cosma5` is NOT mounted on `dine2`/`cosma7`/`cosma8` compute nodes — only on the login node.** A symlink pointing there loads fine from the login node but is silently invisible to `os.path.exists()` inside an sbatch job. Always verify a checkpoint-path fix with `srun -p <partition> python3 -c "np.load(...)"` on the actual compute partition.
- **Write large per-run artifacts to `/cosma8/data/dp004/dc-hick2/diffcmb_results_archive/` and symlink back into the repo's `results/` tree** — confirmed mounted on `dine2` compute nodes, this project's established archive location. Don't write in-place under `/cosma/apps` (quota risk above) and don't use `/cosma5` (not mounted on compute nodes). Distinct from the `/cosma8` dp004 *space* quota (global `~/.claude/CLAUDE.md`) — a headroom concern for large campaigns, not a mount-visibility problem.
- **SLURM `COMPLETED`/exit-0 does not mean the Python script's own logic succeeded** — always check the `.err` file for a traceback even on a clean SLURM exit.
- **dine2/cosma8 reused nodes need a job-private `$TMPDIR`** (autograph cache collision) — every pilot sbatch script sets this.
